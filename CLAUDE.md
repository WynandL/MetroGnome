## Architecture Overview

**MetroGnome** is an Android metronome app with a rhythm game. Single-module Kotlin/Compose project targeting SDK 37, min SDK 24.

**Package vs applicationId, a recurring trip-up:** source lives under `com.example.metrognome` (the `namespace`), while the published `applicationId` is `com.wynandl.metrognome`. Paths are therefore `app/src/main/java/com/example/metrognome/...`, so a `find` or `grep` against `com/wynandl/` returns nothing and looks like the file is missing. The Play Store id, Firebase config and all external references use `com.wynandl.metrognome`.

### Layer Structure

```
UI (Jetpack Compose screens + Canvas)
    ↓
ViewModels (AndroidViewModel + StateFlow)
    ↓
Audio Engine + Game Logic (Coroutines on Dispatchers.Default)
```

### Key Components

**Audio engine layout** — each engine lives in its own sub-package under `audio/`:

- `audio/metronome/MetronomeEngine.kt` — Raw `AudioTrack` in STREAM mode for sample-accurate timing. Pre-generates a click voice for every sound type, keyed by `soundType` index: free (0 Classic, 1 Hi-Hat, 2 Wood, 3 Warm) and premium (4 Bell, 5 Crystal Bowl, 6 Kalimba, 7 Cowbell), each a synthesized buffer. Runs a blocking write loop on `Dispatchers.Default`. The `onBeat` callback fires **before** the audio write (not after) so the UI callback arrives ~16ms early, keeping Compose animations in sync with sound.
- `audio/rhythm/RhythmDetector.kt`: Mic input via `AudioRecord`, used by all three mic features. A `ClapDetector` tells the metronome click apart from a clap by signature (the 1100 Hz Classic click is low-band dominant; a clap is broadband) and emits **only claps**, so an on-beat clap still scores and a leaked click never does, with no time-suppression window. AEC (Acoustic Echo Cancellation) is enabled when available; NoiseSuppressor is intentionally **disabled** (it would filter claps). Onset timing is localised inside each buffer and mapped to `elapsedRealtime` via `FrameClock` + `AudioRecord.getTimestamp`. Because the classifier is tuned to the Classic voices, mic mode forces the Classic **sound type** (`MetronomeViewModel.setMicSoundOverride` / `effectiveSoundType`); the engine keeps its normal 1100 Hz click and normal 1800 Hz downbeat accent, and `ClapDetector` rejects **both** narrowly (a dedicated 1800 Hz accent band alongside the 1100 Hz click band), so the accent stays clearly audible to the player yet the detector never misreads it as a clap. (The Rhythm Game uses its own engine and plays uniform clicks.)
- `audio/rhythm/RoomNoiseMonitor.kt`: Passive observer of `RhythmDetector.amplitude` (never touches capture/detection). An asymmetric-EMA noise floor (fast-down, slow-up) tells brief claps from a sustained noisy room; exposes `noisy: StateFlow<Boolean>`, which drives `ui/components/RoomNoiseIndicator.kt` during play. The `floor` EMA behind that decision is **private** and there is no `everNoisy` flag, so nothing here is wired to telemetry.
- `audio/tuner/` — Tuner engine: `Tuner.kt` (MPM + FFT pitch detection), `TunerCalibrator.kt` (loopback/reference calibration), `AmbientDetector.kt` (room profiling, speech rejection), `TunerFeedbackConfig.kt` + `TunerFeedbackReporter.kt` (Firestore diagnostic submissions).
- `audio/drone/` — Tuning drone (sustained reference tone for tuning by ear), four files with one job each: `DroneVoice.kt` (pure data: `DroneTimbre`, `DroneBlend`, and `buildVoice()` compiling them into a `VoiceLayout`), `DroneRenderer.kt` (pure-Kotlin block synthesis, no Android), `DroneEngine.kt` (AudioTrack + coroutine + thread marshalling), `DroneState.kt` (the persisted settings value). The split is what makes the synthesis unit-testable on the JVM, including against the app's own `PitchDetector`.
  - **The centre-strand invariant.** Every timbre is a stack of "strands" (whole harmonic series a few cents apart, panned outward, each breathing on its own sub-Hz LFO so the beating never freezes). Exactly one strand per timbre is undetuned, unmoving and centred, and `DroneVoiceTest` enforces it. That is what lets a tone this alive still be an exact pitch reference; put movement on the centre strand and the drone stops being usable for its only job.
  - **Timbres must be harmonic.** A struck-bowl voice with stretched partials was built, sounded good, and was removed: `DroneRendererTest` caught the app's own tuner reading it 13 cents sharp, because an inharmonic series has no single period to find. Do not reintroduce inharmonic partials here; the metronome's Crystal Bowl click can afford them because nobody tunes to a click.
  - **Blend intervals are just, not tempered** (3:2, 2:1). A beatless just fifth is the cue a player listens for; an equal-tempered fifth would beat against itself. A consequence worth knowing: root + just fifth repeats at half the root frequency, so any period-based detector correctly reports the octave below. That is the missing fundamental, not a bug, which is why the blend tests measure each tone on its own frequency instead of running the mix through `PitchDetector`.
  - **Nothing in the audio path steps.** Start/stop are raised-cosine envelopes, note changes glide in the log-frequency domain, level follows a one-pole, and a timbre or blend change crossfades between two live voices. The crossfade is deliberately **linear**, not equal-power: the two voices share a fundamental and are strongly correlated, so their amplitudes add and a square-root law bulges audibly mid-change. `DroneRendererTest.noTransitionProducesADiscontinuity` measures every transition against the steepest step the steady tone itself takes.
  - **Sub-cent claims are measured, not detected.** `PitchDetector` carries a few cents of uncalibrated bias (that is what the tuner's calibration exists to remove), so it cannot be the yardstick for accuracy finer than that. The renderer tests pin frequency exactly via a phase-difference measurement across two halves of a capture, and use `PitchDetector` separately, at a 5-cent bar, to prove the harmonics and strands do not pull the perceived note off its fundamental.
  - **The note picker is a drawn one-octave keyboard with no letters on it**, which only works because the naturals are light (`AppColors.keyNatural`) and the sharps near-black. The first version drew both in shades of the same dark violet on the theory that the black-key groups of two and three would orient the eye; they cannot orient anything they are not visibly distinct from, and the dev reported it read as an unexplained row of blocks. If a drawn control is carrying meaning instead of a label, the contrast carrying that meaning is load-bearing, not styling.
  - **The panel opens expanded on a first visit**, and `TunerViewModel.droneExpanded` (SharedPreferences `drone_panel_expanded`, defaulting true) then keeps whatever the user last chose. Shipped collapsed first: the timbre, blend and level controls were discoverable only by finding a chevron, and the header's own "F2 . Reed" readout consequently read as a bug, since it named a setting with no visible way to reach it. People do not go exploring, so a feature worth having is worth showing once. `DronePanel` takes `expanded`/`onExpandedChange` as parameters rather than holding the state, since the ViewModel is what persists it.
  - `NoteNames.frequencyOf(midi, referenceHz)` (added with this feature) is the single place a named note becomes a frequency, so the tuner's reference pitch moves the drone's tone by the same arithmetic that moves the needle's target. `DroneState` stores a MIDI number, never Hz.
- `audio/selftest/` — Acoustic-loopback mic self-test ("Groove Check"): `MicSelfTest.kt` plays clicks/claps through the speaker, listens back, and grades the device (GOOD_FIT / USABLE / NOT_FIT). Design principle: the test's job is to *calibrate* the device as far as possible, not to disqualify it - a device fails only when nothing short of magic would fix it, never because a shipped default happened to be wrong for it. Discrimination's hard gates are inseparability (both spectral axes overlap, tolerating a `SEPARABILITY_MIN_FRACTION` minority of outlier claps rather than one flaky sample) and `MIN_CLAP_ONSET_RECALL` (claps not registering as onsets at all, before classification); a low classified click-reject/clap-detect rate on an otherwise-separable device is advisory only (`NoteCode.CLICK_LEAK_CALIBRATED`/`CLAP_MISS_CALIBRATED`), not a failure. The scoring phase reclassifies captured onsets against THIS run's own just-derived per-device thresholds (`deviceClapBandRatio`/`deviceClapFlatnessMin`) rather than the shipped defaults capture ran with all along - so a device is graded on what it will actually do once calibrated, not on its out-of-the-box fit. Small-sample recall bars (`MIN_CLAP_ONSET_RECALL`, `OUT_OF_BAND_MIN_RECALL`) tolerate one miss out of ~12 trials rather than demanding a literally perfect run. On PASS, `SelfTestCalibrationStore` persists the latency constant plus per-device `ClapDetector` thresholds for both acceptance axes (`clap_band_ratio`, `clap_flatness_min`); `MicCalibration` is the single read surface all three mic features use. `SelfTestThresholds.GATE_LOGIC_VERSION` (currently 4) stamps stored verdicts - bump it on any gate change that could flip outcomes (a stale FAIL then reads as never-tested and the check is re-offered; a PASS is never invalidated). Diagnostics are `NoteCode` entries (short id + looked-up text, e.g. `D2`/`S1`), never raw sentences, so Firestore rows stay one line; codes exist for calibration offsets, thin-but-passing margins (`THIN_SEPARATION_MARGIN`), and near-limit passes (`NEAR_VOLUME_FLOOR`/`NEAR_NOISE_CEILING`) as well as hard failures. Outcomes report anonymously to Firestore `mic_self_test` via `cloud/MicCheckReporter`, including spectral margins, the tuned thresholds actually used, and a human-readable SAST timestamp alongside the raw epoch.
- `audio/dsp/` — Shared DSP building blocks used by the engines: `FFT.kt`, `PitchDetector.kt`, `ClapDetector.kt` (spectral click-vs-clap, the only onset path mic mode uses; accepts a clap on flatness OR band-ratio, and both thresholds are per-device-calibratable constructor params fed from `MicCalibration`), `BiquadFilter.kt`.

**Groove Check permission recovery** (added 2026-08-10, shipped v5.17; consolidated 2026-08-14, v5.18/72): `MicCalibration.isActive` is a SharedPreferences-only check (`enabled && isCalibrated`) — it says nothing about whether the OS still actually holds `RECORD_AUDIO`. That gap matters because an uninstall/reinstall restores SharedPreferences via Android's default app-data backup (nothing in this repo excludes them — see `AndroidManifest.xml`'s `dataExtractionRules`/`fullBackupContent`, both pointed at empty rule files) while Android *never* restores runtime permission grants, so `isActive` can read true with the mic actually inaccessible. `ui/components/MicPermissionRecovery.kt` (`rememberMicPermissionRecovery()`) is the single shared source that guards against this, reading `ContextCompat.checkSelfPermission` live rather than trusting the flag — it replaced three separately-duplicated copies of the same permission-launcher block (in `SettingsScreen.kt`, `MetronomeScreen.kt`, and `RhythmGameScreen.kt`) that had drifted apart in a way that let the same underlying bug re-appear in two of the three places even after the first was fixed. It exposes two entry points, used by all three call sites:
- `startWithMicPermissionCheck(start)` — wraps a session-start action: `MetronomeScreen.kt` (Practice's and Speed Trainer's Start actions) and `GameCard` in `RhythmGameScreen.kt` (each difficulty tap). If the flag says on but the live permission is missing, it fires the real permission dialog immediately at the moment of starting and only calls the actual start function once that resolves, so a granted permission takes effect for that same session, not just the next one.
- `fixPermission()` — what `ui/components/MicTimingNudge.kt`'s "needs microphone access · tap to fix" pill (Practice/Speed Trainer/Rhythm Game) and `SettingsScreen.kt`'s Groove Check toggle both call on an already-calibrated device: a lightweight re-request (or a hop to App Settings if permanently denied), deliberately never the full Groove Check — the device already proved itself once, so re-running the whole onboarding flow would be a confusing, needless detour. `MicTimingNudge` shows a dedicated "needs microphone access" state instead of either lying ("Groove Check is on") or going silent when this fix action isn't wired (a non-interactive "Fix in Settings" note instead).
- `audio/NoteNames.kt` — Shared music-theory utility (note name ↔ frequency mapping); stays at the `audio` root because all three engines may reference it.

**Drone / microphone exclusivity** (added 2026-09-03). `TunerViewModel.resumeListening()` is the *only* place `tuner.start()` is called outside the initial entry point. Three separate things can hold the audio path: the screen having navigated away (`listenIntent`), a calibration run, and the drone. Before this there were two independent resume paths (`startListening` and the tail of `runCalibration`) that each knew about a different subset, which is exactly the shape of the bug the `MicPermissionRecovery` consolidation fixed on the permission side. Every path that finishes one of those conditions now calls back into `resumeListening()`, which re-checks all three plus the live permission; no caller has to remember the others and none can re-open the mic behind another's back.

Starting the drone closes the mic, deliberately: the tuner would hear the app's own tone through the speaker and lock onto it, reporting a perfectly in-tune note that is entirely its own output. The needle has nothing to add while a reference tone is sounding, since tuning by ear against it is the whole point. `DronePanel` says so on screen ("Tuner needle paused" / "The needle returns when you stop the drone.", deliberately without the reason: a user needs to know it is intentional and reverses itself, not why), and `AmbientPanel` takes a `listeningPaused` flag so it shows "Paused for the drone" with no state icon lit, rather than sitting on "Getting ready…" as though it were stuck. `runCalibration` stops the drone outright, since loopback calibration measures what comes back from the speaker.

`stopListening()` (fired when the Tuner tab is left) deliberately does **not** stop the drone: a sounding drone carrying over to the metronome tab is the practice mode the two make together, matching how the metronome itself keeps playing across tabs. It ends on an explicit stop or in `onCleared`. `DroneState.playing` is never persisted — the drone is opt-in on every launch, and the mic behaves normally until the user starts one on purpose.

**Billing error surfacing and paywall copy placement** (2026-08-24). `BillingManager.purchaseError: StateFlow<String?>` is set on any `BillingResponseCode` outside `OK`/`USER_CANCELED`/`ITEM_ALREADY_OWNED` - across the `purchasesUpdatedListener` else-branch and every early-return failure inside `launchPurchaseFlowFor` (failed product query, missing product details, failed `launchBillingFlow`) - each mapped to a short user-facing string by `errorMessageFor`. Before this, those paths only reset `_isPurchasing` with no message, so a failed purchase (network blip, store unavailable) looked identical to nothing happening. `SettingsScreen` shows it via a one-shot `Toast` (`LaunchedEffect(purchaseError)` + `vm.clearPurchaseError()`), the app's existing pattern for this kind of transient feedback - not a new dialog/banner. `PurchasableItemDef.unlockAlternative` (the free-earn path, e.g. "or play the metronome for 6 hours" for Glissie) renders **only** inside the purchase dialog (`PurchasableItemDialog`'s `belowDescription` slot), never in the Settings "Items" row above it - a deliberate, easy-to-forget split: the row is the pitch, the dialog carries the fine print.

**Drone usage tracking and the Drone Bee** (2026-09-03). Drone sounding time is its own counter (`MetroItemTracker.addDroneSeconds`, prefs key `drone_seconds`), credited in ten-second slices by `TunerViewModel.startDroneTimer` while the tone plays. Deliberately separate from `tuner_seconds` even though both happen on the Tuner screen: the two are mutually exclusive by design (the drone closes the mic), they earn at different rates, and an item asking for drone time must not be satisfiable by leaving the needle running. A paywall audition never counts, or the item would be farmable by opening a dialog.

**It earns 1 Gnote/minute capped at 30/day, the lowest rate in the app**, where everything else caps at 90. The drone is the only activity that asks nothing of the user once started, and it can sound at the same time as the metronome, which is already earning; matching the metronome's rate would have made "start both and walk away" the best-paying thing in the app.

**`PointsBannerQueue.postSilentEarn()` / `silentEarn` exists because of the cached-counter trap** documented under Gnotes/Points System. Continuous earners credit the tracker with no banner (a banner every ten seconds is intolerable), so the displayed total goes stale. The metronome got away with refreshing its own `_gnoteCount` inside its play loop only because the counter and the loop are in the same ViewModel; the drone's loop is in `TunerViewModel` and cannot reach it. Any credit path anywhere can now post this, and `MetronomeViewModel` (which owns the displayed total) recomputes. Use it for any future continuous earner rather than inventing a second private arrangement.

The reward is `items/DroneBee.kt` at `UnlockCondition.DroneSeconds(1_800)` (30 minutes): a bumblebee patrolling a figure of eight, because a drone is both a held note and a bee. Two art notes worth keeping: the path is a closed Lissajous rather than the random drift the Fireflies use, since a bee's motion has to look purposeful; and the body's heading comes from the derivative of that path, without which the sprite slides sideways through the corners and reads as a decal being dragged around. **One unit is `size.height / 18`, so a body under about 0.9u stops reading as a bee and becomes a striped dash** - it was first drawn at 0.62u and had to be scaled up.

**A moving item's motion must be expressed in `u`, and `previewRadius` must contain the whole path.** `ItemPreviewCanvas` (in `UnlockCelebrationOverlay.kt`, used by the collection cards, the unlock popup and the Settings dev previews) crops around `previewCenter` with a `u`-relative `previewRadius`, then zooms by `minDimension * 0.40 / radius`. If the item's drift is a fraction of the canvas instead, the two scale apart with aspect ratio: the Drone Bee's patrol was `0.085 * width`, which on a 200x150 collection card put its excursion at 96px inside a 100px half-width, so it spent half its loop outside the frame while looking correct in the taller Settings preview. Fireflies get away with canvas fractions because they genuinely are spread across the whole scene and their `previewRadius` is `6u`. For a single moving object, tie the span to `u` and size `previewRadius` to span + half the item, which makes containment arithmetic rather than luck.

**Analytics.** `drone_started` (note label, timbre, blend, reference_hz), `drone_stopped` (duration_seconds), `drone_voice_changed`, and `drone_voice_previewed` (product_id), all fired from `TunerViewModel` and defined in `AnalyticsTracker` like every other event. The start/stop pair mirrors the metronome's and the tuner's exactly, including the caveat they share: the stop event only fires on an explicit stop, so a session ended by the process dying is not counted. The note is sent as its label ("A3") rather than a MIDI number so a report reads without a lookup table, and it is the parameter worth watching (a pile of E, A and D says guitarists). `drone_voice_previewed` paired with the Play Console's sales for the same product id answers the only question a paywall really raises: of the people who heard it, how many bought. The Drone Bee's unlock needs nothing new, since `checkForNewUnlocks` already logs `item_unlocked`. Per-10s Gnote credits are deliberately not logged, matching the metronome: six events a minute of noise for a number already derivable from the durations.

**Adding an `UnlockCondition` variant: two of the four files will not remind you.** A new variant needs a counter in `MetroItemTracker` (writer, reader, `isUnlocked` branch, `resetAllProgress` line), a `displayText()` branch, and then `points/ConditionPoints.kt` (two functions) and `ui/components/metro_items/UnlockProgress.kt` (two functions). **`UnlockProgress.kt` is the one that gets missed** - it was, when `DroneSeconds` was added, and only the exhaustive `when` caught it. Nothing on the feature side references that file, so it never turns up in a search for the thing being built, and it drives the collection's progress bars, a screen away from wherever the work is happening. Both files are exhaustive `when` blocks on the sealed class, so the compiler is the safety net: expect those two build errors when adding a condition, and welcome them. The same checklist is repeated in `UnlockCondition.kt`'s own KDoc, which is the file you open first.

**Monetised drone voices** (2026-09-03). Reed and String (timbres) and Fifth (blend) are paid; Pure, Warm, Root and Octave stay free, so the drone is fully usable without paying. `billing/PremiumDroneDef.kt` maps the enum entries to products and is the only place that knows which voices cost money, keeping `audio/drone/` free of billing knowledge. Four things are worth knowing:

- **They share `BillingManager.SOUND_PRODUCTS`.** That set is "things you buy that make a sound", not "metronome clicks", so drone voices are priced, queried, reconciled, acknowledged and restored by the code that already does it for the clicks rather than a fourth near-identical family of flows. Nothing enumerates that set to build UI (the registries do that), so extending it is safe.
- **There is still exactly one `BillingManager`,** owned by `MetronomeViewModel`. `TunerViewModel` does not make its own: two clients would mean two listeners, two caches and two chances to disagree about what has been paid for. `MainActivity` gathers the state into a `billing/PurchaseStore` snapshot for `TunerScreen`, and pushes owned ids into `TunerViewModel.setOwnedProducts`, which reverts a locked timbre or blend to the free fallback (crossfading, so a refund mid-note does not cut). **That guard must not skip when the set is unchanged**: the field starts empty, so for a user who owns nothing the first push compares equal, and an early return would leave a paid voice selected from a previous install free to sound.
- **The failed-purchase Toast moved to `MetroGnomeApp`.** It lived in `SettingsScreen`, which was correct while Settings was the only place you could buy anything. With a second selling surface, a failure started from the Tuner would have gone unseen and then appeared as a stale toast the next time Settings opened.
- **An audition replaces the live voice, it never layers over it.** `DroneRenderer.setVoice` moves the old voice to `outgoing` and crossfades over 200 ms, after which `crossfade` reaches 1, `outgoing` is dropped and its level is multiplied by exactly zero. Measured residue is about -175 dB (the floating-point floor), and `DroneRendererTest.anAuditionReplacesTheLiveVoiceRatherThanLayeringOverIt` guards it by sounding Reed, auditioning Pure, and checking that Reed's third harmonic is gone. The dev asked this directly because it is genuinely unanswerable by ear: the two voices share a fundamental and the changeover is a fade. **The UI answers it too** - `PreviewActionButton` takes an `active` flag, and while an audition sounds the button turns gold and reads "Sounding <voice> on its own". Without that signal a listener has no way to tell a replacement from a blend, which is exactly the doubt that came up.
- **The preview drives the real engine, not a sample.** `MetronomeViewModel.previewSound` fires a one-shot buffer because a click plays over anything; a drone is sustained and owns the speaker, so `TunerViewModel.previewDroneVoice` starts the actual drone at the note already chosen and the mic stands aside exactly as for a real session (a fourth holder in `resumeListening`'s list). If the drone is already sounding, the previewed voice crossfades in over the live one and back out, so the two can be compared directly. Its restore runs in a `finally` under `NonCancellable`, so a dismissed dialog or a real start mid-audition can never leave the previewed voice sounding.

Shared with the click sounds so the two paywalls cannot drift: `ui/components/PremiumChip.kt` (the gold star, which marks *premium* and stays after purchase, not *locked*) and `ui/dialogs/PremiumPurchaseDialog.kt`'s `AudioShowcase` (extracted from `SettingsScreen`'s private `SoundShowcase`). The dialog itself is the same `PremiumPurchaseDialog` down to the audible-preview slot.

**Premium sounds and instrument affinity.** `billing/PremiumSoundDef.kt` holds `PREMIUM_SOUND_REGISTRY`, the single source for purchasable sounds (product id, display name, description, `soundType` index). Settings renders a chip plus a paywall dialog per entry automatically; billing reconciliation is generic over `BillingManager.SOUND_PRODUCTS`. To add one, follow the 5-step recipe documented at the top of `PremiumSoundDef.kt`. `ui/components/instruments/` is a text-free instrument-affinity nudge with one manager, `InstrumentAffinity` (maps a `soundType` index to the instruments it suits). Icons are Lucide glyphs (ISC, see `THIRD_PARTY_LICENSES.md`) rendered from path data via `PathParser` in `InstrumentGlyphs`. `InstrumentAffinityRow` sits above the Settings sound chips (matching instruments glow gold, the rest dim as the user taps through sounds); `InstrumentAffinityBadges` shows just the relevant instruments inside the premium paywall dialog so an unowned sound still advertises its fit.

**`theory/Meter.kt`** — Single source of truth for time-signature music theory (pure Kotlin, no Android deps, shared by the engine/ViewModel/Settings UI). Classifies a `Meter(top, bottom)` as SIMPLE (top 2-4), COMPOUND (top a multiple of 3, ≥6), or IRREGULAR (everything else: 5, 7, 8, 10, 11...) — classification depends only on the top number, never the bottom (3/8 is simple, not compound, despite the 8). `label()` renders this for display: "Simple quadruple", "Compound duple", and for IRREGULAR either **"Odd"** (when the top number is actually odd — 5, 7, 11, 13) or **"Irregular"** (when it isn't — 8, 10, 14, 16). Do not collapse this back to a single "Odd" label for the whole IRREGULAR class: "odd meter" specifically means an odd number of beats, and mislabeling an even one is a factual music-theory error a musician would catch (caught and fixed 2026-08-14, see `MeterTheoryTest`'s parity test cases). `description()` gives the plain-English feel ("Felt in 2+2+3" for 7/8, "Felt in 2, beats split in three" for 6/8), rendered by `ui/components/TimeSignaturePicker.kt` above the accent-cell grid it explains. `beatGrouping()`/`defaultAccents()` derive the natural accent pattern from the same classification (irregular meters default to twos with a trailing three, e.g. 7 → [2,2,3]) — the Settings UI lets the user override any accent, since the "one true" grouping for an odd meter is genuinely contested.

**`viewmodel/MetronomeViewModel.kt`** — Manages play state, BPM, time signature, sound type, volume. Tap tempo requires ≥2 taps within 2.5s. Persists settings to SharedPreferences (`metrognome_prefs`).

**`viewmodel/RhythmGameViewModel.kt`** — State machine: IDLE → COUNTDOWN → PLAYING → RESULT. Notes have 2000ms travel time from spawn to hit line. Hit windows: PERFECT ±50ms, GOOD ±100ms, ALMOST ±150ms (scaled by user tolerance setting). Scoring: PERFECT=100, GOOD=70, ALMOST=30. High scores persisted per difficulty in `rhythm_highscores` SharedPreferences.

**`ui/components/GnomeCanvas.kt`** — Custom Compose Canvas drawing the gnome. Animations (pendulum, bounce, flash, twinkle) are synchronized to `BeatEvent` emissions from MetronomeViewModel. The `feature/metro-cosmetics` branch extends this with a `MetroItem` system: `activeItems`/`onItemTapped` params, tap-hit detection, and separate draw passes for background items, body-attached items, and head-attached items (which bob with the head group).

**Metro's lighting model** (v5.19) — every part of the character is lit by one key light from the **upper-left**, driven from a single place rather than per-feature approximations. `KEY_LIGHT_X/Z` + `rollLambert(nx)` in `GnomeCanvas.kt` give the Lambert term for any horizontally-rolled surface (nx: -1 = left silhouette edge → +1 = right). Note the curve peaks near nx = -0.6 and falls back off at nx = -1, because the lit edge still turns away from the viewer — an evenly-brightening left-to-right ramp never looks right. `rollGradient(fromX, toX, strength) { shade -> … }` is the standard way to apply it; each feature supplies only its own colour ramp (`coneFeltColor`, `beardRollColor`, `browRollColor`, `goldRollColor`, `clothRollColor`, `pantsRollColor`, `shoeRollColor`). The head sphere has its own `skinSphereColor` / `skinFalloffAt` pair, shared with the ears so they match the cheek at the junction.

Hard-won rules, all of which produced visible bugs when broken:

- **`strength` scales with the element.** The raw Lambert term runs to its extremes at the silhouette edges — right for the hat, far too much for a lens or a bow tie, where it stops reading as lit and starts reading as bruised or grubby. Small elements dial it to 0.4–0.55.
- **One object → one gradient; two objects → two.** Lapels, bow tie and sunglasses each span the whole pair with ONE gradient (shading halves separately mirrors the highlight and reads as two light sources). Trousers, shoes and buttons get one each. Shoes additionally take a global falloff across BOTH plus a lift at each shoe's leading edge.
- **Cast shadows must be clipped to what they land on.** Several features overhang the head — the brim (2.1u vs a ~1.5u head), the moustache (1.58u vs a ~1.08u jaw) — so an unclipped shadow hangs in the sky. `hatShadowSurface(u)` = head ∪ hair ∪ ears is the brim's target; leaving any part out leaves that part lit beside a shadowed face.
- **Don't stroke a specular edge onto a flat shape.** Tried and reverted three times (hat brim rim, torso edge ×3): a rim needs surface detail to sit on, and a constant-alpha stroke around a closed curve reads as a halo. The fill's roll-off carries these alone.
- **Union coincident shapes instead of abutting them.** The hat is `cone ∪ brim` and the moustache is `wing(-1) ∪ wing(+1)`, each shaded in one pass. Android does not antialias clip edges, and *any* opaque repaint beside already-shaded pixels leaves a 1px lighter seam (its antialiased edge gets ~half the shading of its neighbours). Overlapping does not cure this — only removing the internal edge does.

**`ui/components/GnomeCanvas.kt`** — Custom Compose Canvas drawing the gnome. Animations (pendulum, bounce, flash, twinkle) are synchronized to `BeatEvent` emissions from MetronomeViewModel. The `feature/metro-cosmetics` branch extends this with a `MetroItem` system: `activeItems`/`onItemTapped` params, tap-hit detection, and separate draw passes for background items, body-attached items, and head-attached items (which bob with the head group).

**`ui/components/GoldSlider.kt`** — The tuner's slider: a gold thumb whose halo brightens on every change and springs back, on a rail whose active portion is a gradient (dim at the origin, bright under the thumb) with a radial bloom where the two meet, plus an optional `markerFraction` tick for a rail with a canonical position on it (the reference pitch's 440 Hz). Extracted from `ReferencePitchCard` when the drone panel needed the same control; the drone had shipped with a stock Material slider and the two sat on one screen looking like different controls for the same gesture. Any new slider on the Tuner screen uses this. `SettingsScreen`'s `SettingsSliderRow` is deliberately left alone: it is a different screen with a plain list-row idiom, and pulling it in would be a redesign rather than a de-duplication.

**`ui/components/RaisedControl.kt`** — Shared raised-key treatment for the metronome's primary control row (steppers, play/pause, TAP). Three layers: a vertical gradient across the face (lifted top, sunk bottom), a hairline rim that is bright on the top edge and dark on the bottom (a *uniform* outline reads as a drawn border — same trap as the character's edge lighting), and nothing else. No blur, glow or drop shadow: on a background this dark a shadow is invisible, and adding one turns "raised" into "glassy". Both shading colours are **derived from the `tint` parameter**, so one component serves neutral steppers, purple TAP, and a play key that animates purple↔red with the highlight tracking it automatically. The secondary icon row is deliberately still flat (hierarchy).

**`ui/components/Seal.kt`** — The app-wide "earned and verified" mark: a scalloped rosette with a check, used wherever something is certified (Groove Check pass, achieved streak days, unlocked collection items). Three layers: `SealStyle` (all visual knobs: colors, alpha, scallop count/depth, check stroke; presets `Emblem`, `Badge`, `SealStyle.halo()`), `DrawScope.drawSeal` (the core, for seals inside a larger Canvas), and the `Seal` composable (self-contained element with slow drift rotation on the shared `SEAL_DRIFT_PERIOD_MS` clock, optional one-shot stamp `entrance`). Only the rosette rotates - the check always stays upright. New uses must adapt a `SealStyle`, never redraw the silhouette.

**`ui/components/metro_items/`** — Cosmetic item system (feature branch only).

- `MetroItem` interface: `draw(u, cx, baseY)`, `hitCenter(u)`, `hitRadius(u)`, `isBodyAttached`, `isHeadAttached`, `previewCenter(canvasW, canvasH, u, baseY)`, `previewRadius(u)`. Background items override `previewCenter`/`previewRadius` to define a tight zoom window for the unlock popup preview; body-attached wearables use `hitCenter`/`hitRadius` for the same purpose.
- `METRO_ITEM_REGISTRY` — single source of truth pairing each `MetroItem` with an `UnlockCondition`. Registry order controls background draw layering (back → front); do not reorder without checking visual correctness.
- `MetroItemTracker` — reads/writes SharedPreferences `"metro_cosmetics"`. Counters: `metronome_seconds` (incremented every 10s while playing), `games_completed` (incremented on game end), `first_launch_ms` (set once on first init). Celebration tracking: `celebrated_item_ids` — written only when the user dismisses the popup ("Sweet!" button), not when the unlock is detected. This ensures a popup bug never permanently silences an earned reward. `markCelebrated` also emits on a companion-object `celebrationDismissed: SharedFlow` — a single app-wide signal (MetronomeScreen/RhythmGameScreen/SettingsScreen each hold their own tracker instance over the same prefs file, so this is how one shared collector in `MainActivity` hears a celebration from any of them; currently used to fire the one-time notification-permission ask, see Notifications below).
- `UnlockCelebrationOverlay` — full-screen animated popup (confetti + spring card). Collected via `vm.newlyUnlocked: SharedFlow` into a `mutableStateListOf` queue in each screen; shown one at a time. `markCelebrated` is called in `onDismiss`, not during emit.
- `ItemPreviewCanvas` — 220×170dp canvas inside the overlay. Background items: translate+scale transform using `previewCenter`/`previewRadius`. Body-attached items: translate+scale using `hitCenter`/`hitRadius` with a boosted u (`size.height/5f`).

**Dev tools in `SettingsScreen`** (visible in debug builds only, gated by `BuildConfig.DEBUG`):
- Toggle cheat mode — all items unlocked while active
- Preview popup for any registry item (cycles with index button)
- Show unlock rules — scrollable dialog sorted easiest → hardest, built from registry at runtime
- Reset all progress — wipes `metronome_seconds`, `games_completed`, `first_launch_ms`, `celebrated_item_ids`

### Notifications

`notifications/` holds all FCM/permission logic — nothing outside this package calls a Firebase Messaging API directly:

- `MetroFcmService` — `FirebaseMessagingService` subclass; builds and posts the notification (guarded by a live `POST_NOTIFICATIONS` check, since a granted-at-send-time assumption can be stale). Overrides `onRegistered(installationId)`, not `onNewToken(token)`, to re-subscribe to the broadcast topic on every Firebase Installation re-registration — confirmed 2026-08-14 directly against the resolved `firebase-messaging` bytecode that `onNewToken` is `@Deprecated` in this version, superseded by the `onRegistered`/`onUnregistered` pair. Lint's built-in `MissingFirebaseInstanceTokenRefresh` check doesn't know about that replacement (it only recognises `onNewToken` by name) and is suppressed on the class with an explanation - do not "fix" that finding by adding `onNewToken` back.
- `NotificationChannels` — the single `"general"` channel, id must match `default_notification_channel_id` in `AndroidManifest.xml`. Created idempotently in `MetroGnomeApplication.onCreate`.
- `NotificationTopics` — broadcast model: every consenting device subscribes to one topic, `"all_users"`. No per-device tokens are collected or stored — a message sent to that topic from the Firebase Console (or a Firestore-triggered Cloud Function via the Admin SDK) reaches everyone with zero backend. `MetroGnomeApplication.onCreate` syncs subscription state with the live permission on every launch in both directions (subscribe if granted, **unsubscribe if not**, added 2026-08-14) - the unsubscribe half matters because revoking notification access happens entirely in system Settings, outside any in-app callback, so without it a device that revoked access would stay subscribed (and keep waking for pushes `MetroFcmService` already silently drops) indefinitely.
- `NotificationPermissionState` / `rememberNotificationPermissionState()` — live `POST_NOTIFICATIONS` state (always `true` pre-API 33) plus request/open-settings actions, mirroring the mic-permission pattern in `TunerScreen.kt`. Owned once in `MainActivity`, passed down to `SettingsScreen`.
- `NotificationOptInTracker` — one-shot flag for whether the contextual soft-ask (below) has ever been shown.

**Permission ask, two paths, deliberately not more:**
1. **Contextual, once ever** — fired the first time the app is opened on a 2nd distinct calendar day (`UsageDayTracker.distinctDaysCount() >= 2`, checked in `MainActivity`'s `ON_RESUME` effect - the same counter `LoyaltyDays` items use). Chosen 2026-08-14 over the original first-item-unlock trigger: that one only reached users who engaged with the cosmetic-item system, so plain-metronome users and anyone who already owned every item before this feature shipped could never be asked. Shows `ui/dialogs/NotificationOptInDialog.kt` (a plain "Enable / Not now" card) before ever spending the real system permission dialog. Never re-shown automatically after that.
2. **Self-serve, always available** — the "Notifications" row in `SettingsScreen`, always reading the live OS permission (never a stored flag — tapping while granted opens the system per-app notification screen, since an app can't revoke its own grant).

### What's New

`whatsnew/` — `AppWhatsNew.ALL` is the registry of major-version popup keys (`v3`, `v4`, `v5`); only major versions get one, never minor/patch. `WhatsNewTracker` persists which keys a device has confirmed and hands `MetronomeViewModel` the single next-pending key via `pendingKey()`; `MetronomeScreen` shows it via `WhatsNewOverlayDispatcher` (`ui/overlays/WhatsNewOverlay.kt`) ahead of the item-unlock queue but behind a pending practice result. **Brand-new installs never see any What's New popup** (changed 2026-08-14): the fresh-install guard in `WhatsNewTracker.init` pre-marks every key, including the latest, as already shown. Previously it left the latest key open so new installs got the last major version's popup as a de facto feature ad - removed because "NEW IN VERSION X" copy has no meaning to someone with no "before," and first cold open is the worst point in the funnel to spend a blocking modal advertising one feature out of several the user doesn't know about yet. An upgrading existing user is unaffected either way, since their prefs are never empty at that check.

### Color System

All colors are centralized in `ui/theme/Color.kt`. Do **not** add raw `Color(0xFF…)` hex literals to screen or component files — always define in the appropriate object first.

- **`GnomeColors`** — gnome character art palette (skin, hat, suit, shoes, hair, baton, FX). Used exclusively inside `GnomeCanvas.kt` draw functions. Most entries now come in lit/base/shadow triples feeding the ramps described under *Metro's lighting model* — e.g. `skin`/`skinHighlight`/`skinDark`/`skinShadow`, `hatRedLight`/`hatRed`/`hatRedDark`/`hatShadow`, `shoeLight`/`shoe`/`shoeDark`, `tieLight`/`tie`/`tieDark`. `skyRim` is the scene's ambient bounce off the night sky (named for the sky, not the hat that first needed it); `nostril` exists because `skinDark` is *lighter* than the shaded lower half of the nose and tinting with it lifted the nostrils into light dots.
- **`AppColors`** — UI chrome colors shared across screens and components: backgrounds (`background`, `surface`, `surfaceVariant`, `surfaceDeep`, `surfaceDim`, `surfaceActive`), text (`textPrimary`, `textSecondary`, `textMuted`, `textSubtle`, `textDim`, `textAccent`, `textMutedBlue`), brand (`gold`, `primaryPurple`, `mediumPurple`, `deepPurple`, `darkPurple`, `danger`), controls, stop-action colors, overlay preview gradient, confetti list, and dev-tool colors.
- **`GameColors`** — rhythm game semantics: hit quality (`good`, `almost`, `miss` — gold = `AppColors.gold` for PERFECT), note tints (`noteAmber`, `notePurple`), beat dots, mic equalizer (`eqQuiet`), hit line idle (`hitLineIdle`), range label blue (`rangeBlue`).
- **`ItemPalette`** — shared cosmetic-item drawing colors: gold trio (`goldLight`, `goldMid`, `goldDark`) used by GoldChain/GoldEarring/LuxuryWatch; wood duo (`woodBrown`, `woodLight`) used by ForestTree/TorchPost.

Item-specific colors that are unique to one file (mushroom teal, firefly glow, flower petals, moon, gem, watch strap, torch flame/grass) remain as `private val` constants inside each item's object — do not extract these unless they become shared.

**`drawable/ic_launcher_foreground.xml`** — Vector launcher icon foreground derived from GnomeCanvas.kt (u=9, cx=54, baseY=164 → 108×108 viewport). All colours match `GnomeColors`. Hat rotated 11° via `<group android:rotation="11">` matching `drawHat`. Do **not** simplify to circles/rects — the paths are intentionally accurate. It deliberately does **not** track the v5.19 shading work: a vector drawable cannot express the sweep gradient the hat uses, and at 48dp the flat fills read fine — so treat the icon as its own flat-shaded rendition, not a copy that has fallen behind.

### Typography trap

`Typography.bodyLarge` in `ui/theme/Type.kt` declares `fontSize = 16.sp` **and an absolute `lineHeight = 24.sp`**, and Material3 provides it as the ambient text style. A `Text` that overrides only `fontSize` keeps the 24.sp line height — so a 12.sp headline lays out on double-height lines. This is invisible until the string wraps, then shows as a gaping gap (found in `MicTimingNudge` 2026-08-15). **Always set `lineHeight` alongside any `fontSize` override.** A root fix (`lineHeight = 1.5.em`, identical at 16.sp but proportional everywhere else) is deliberately not applied: it would also change text set *larger* than 16.sp, where the cramped 24.sp is currently load-bearing for layout.

For a 12.sp headline over a 10.sp subtext line (the recurring pattern in `MicTimingNudge` and `DailyBonusCta`), set `lineHeight = 16.sp` on the headline (not `12.sp` matching the font size 1:1) — tried at `12.sp` first, but on-device that read as visibly cramped once installed; `16.sp` gives a small amount of natural leading without reopening the original 24.sp gap.

### Gnotes / Points System

`points/PointsManager.getSnapshot()` never caches - every call reads live SharedPreferences via `MetroItemTracker` and recomputes the total, so any code holding a fresh `PointsManager` always sees the true current value. The trap is one layer up: `MetronomeViewModel.gnoteCount` (a `StateFlow<Int>`, the single source both the Home pill and the Rhythm page's `PointsCard` read from) is a **cached** copy of that total, and it only gets pushed a new value when something explicitly writes `_gnoteCount.value = pointsManager.getSnapshot().total` - either a `PointsBannerQueue` event (Practice/Rhythm/Tuner/ad-watch completions all post one) or `recordUsageDay()` (fired on `ON_RESUME`). Free-run metronome play credits Gnotes silently every 10s via `itemTracker.addMetronomeSeconds(10)` in `startPlayTimer()` with **no** banner event, so before 2026-08-17 the displayed total could sit stale for minutes at a time - fixed by also refreshing `_gnoteCount` inside that same 10s loop. Any future code path that credits Gnotes without going through `PointsBannerQueue` needs the same explicit refresh; recomputing `PointsManager().getSnapshot()` fresh on next screen-open is not enough; the cached `StateFlow` is what's actually on screen.

`ui/components/GnoteTickFlair.kt` - shared "Gnotes just ticked up" flair: wrap any view showing a live Gnotes total in `GnoteTickFlair(count = ...)` and it fires a small gold spark burst whenever `count` rises while it's on screen. Never fires on first composition (the value it mounts with becomes its baseline), so it composes safely alongside a caller that already animates the same value on mount (e.g. `PointsCard`'s own 0→total roll-up) - the two don't fight because the flair only reacts to a genuine rise *after* mounting, not the reveal itself. Purely additive (drawn via an overlaid same-size `Canvas`); overshoots small unclipped views (the Home pill) but is contained by any ancestor that clips (the Rhythm page's card).

`ui/components/DailyBonusCta.kt` - shared rewarded-ad "watch a clip for bonus Gnotes" row plus its confirmation (`DailyBonusConfirmDialog`), used identically by `GnotesInfoDialog` (Home) and the Rhythm page's `PointsCard`. Previously this was two independently-drifting copies of near-identical Compose code; now both call sites pass state in and get the same copy/visuals for free. The reward badge is a pulsing **ring drawn in a `Canvas` that expands past the badge's own edge** into the surrounding background, not a `Modifier.border` sitting on the badge - a same-color border directly on a solid gold fill is gold-on-gold and barely reads regardless of alpha; the ring only becomes visible by never overlapping the fill it's supposed to contrast with.

### Navigation

`MainActivity` hosts a `NavigationSuiteScaffold` with 4 tabs (`AppTab`): Gnome (metronome), Tuner, Rhythm (game), Settings. No `NavController` - `currentTab` is a single `rememberSaveable` enum in `MetroGnomeApp`.

**FCM deep links** (added 2026-08-14): an `openTab` data key on an FCM message (value = an `AppTab` name, e.g. `"rhythm"`, case-insensitive) opens straight to that tab on notification tap. `MainActivity.EXTRA_OPEN_TAB` is the intent-extra key; `MetroFcmService` attaches it to the `PendingIntent` when it builds the notification itself, and for the case where the system posts the notification directly instead (background app, notification+data payload - see that file's kdoc), the FCM SDK copies the data payload onto the launch intent automatically, so no separate handling is needed there either. `MainActivity` is `launchMode="singleTop"` specifically so a tapped notification while the app is already running reuses the instance via `onNewIntent` rather than tearing down and recreating every ViewModel (which would kill an in-progress metronome/tuner/rhythm session). `MetroGnomeApp(openTab, onOpenTabConsumed)` applies it via a `LaunchedEffect` and immediately consumes it (resets to null) so a second notification tap for the same tab still re-triggers. **All tab switching, including this deep link, goes through one `switchTab(tab)` local function** in `MetroGnomeApp` (extracted 2026-08-14 during a pre-publish audit) - the deep-link `LaunchedEffect` originally set `currentTab` directly, silently skipping the RHYTHM-leave guard (`rhythmVm.stopGame()`) and the Tuner/Settings review-prompt trigger that the nav bar's `onClick` already had. Any future tab-switch side effect belongs in `switchTab`, not duplicated at each call site.
